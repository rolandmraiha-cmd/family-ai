# Startup investigation: 4 November 2026

The larger Gemma now uses `ENFORCE_EAGER=true` on the existing endpoint
`936leprwfzb9gr`. Two fresh-worker probes observed startup wait falling from
130.697s to 114.498s. This does **not** meet the under-20-second target.

## What changed

- Added eager mode to the full existing environment, preserving every other
  value, including `MAX_NUM_BATCHED_TOKENS=8192`. Live worker logs confirmed
  graph capture and JIT kernel warmup were disabled.
- Recycled the old release with max workers 0 then 1, after the baseline job
  completed. Final min0/max1, idle120s, FlashBoot, model, regions, image support,
  context length and tool parsers remain as before.
- Synced the Gemma JSON's existing live CUDA13 requirement, queue delay1 and
  capture sizes. These three values were already live before the experiment.
- No Qwen, Fast, voice, application, SSH or firewall settings changed.

The installed image is `runpod/worker-v1-vllm:v2.30.1`; live logs confirmed
vLLM0.32.0. In that version eager mode disables compilation, CUDA graphs and JIT
warmup. Existing compilation JSON remains available for rollback; eager mode
overrides its graph settings.

## Why under 20s is still unproven

FlashBoot was already enabled on all four endpoints. RunPod describes its fast
path as resuming a retained worker with weights still loaded. Eviction and
capacity constraints can require a fresh worker, which must import the runtime,
load weights and initialize the engine. Both probes above performed fresh model
loads; the second followed a deliberate release recycle. Neither is a retained
FlashBoot-resume benchmark, a guaranteed latency bound or a natural-resume test.

The baseline spent about 43s between vLLM launch and engine initialization, then
17s loading the model and 53s in profiling/cache/warmup. These phases exceed 20s
even before capacity delays. Model files were already cached; repeating a
download fix would not remove those phases. A40 availability was LOW in the
approved Nordic regions during the audit.

We retained image memory profiling: the supported skip flag transfers memory
sizing responsibility to us and needs separate image/context stress tests.
No network volume, priority-FlashBoot contract, keepalive loop or always-on GPU
was added. Reliable under 20s across cache misses would need a different serving
arrangement or a smaller model that passes the family language requirements.
Keeping a GPU warm introduces ongoing billing and is outside this change.

## Budget and rollback

Two durable ledger operations each reserved USD 0.35, including up to 600s compute
and 120s idle at the conservative USD 1.75/h pool ceiling. Cumulative budget held
rose from USD 11.019672 to USD 11.719672; those figures are estimates, not wallet
spend. Neither response reported a dollar cost. No usage was reset.
The temporary USD 12/day test cap was restored to USD 2/day after each probe;
USD 20/month remained unchanged. No third inference request was submitted.

After the eager job, the larger Gemma naturally returned to zero RUNNING
workers by 21:13:33 UTC, without another recycle. This verifies scale-down for
this observation, not exact provider billing or future FlashBoot retention.
Native authenticated policy/usage/capability checks returned HTTP200 and no
active reservations; all 57 ledger jobs retain their accounting. The 105 Python
and nine JavaScript regression tests pass; the endpoint JSON parses and the
live environment differs from the baseline only by `ENFORCE_EAGER=true`.

To reverse eager mode, remove only `ENFORCE_EAGER` from the complete current
environment, retaining all other values and the capture-size configuration.
Recycle max0 then1 after active work finishes. Do not replace a full environment
with a partial map or copy redacted values back to RunPod.
